01 / Overview

The delivery loop at a glance

Harness coordinates the steps. Git stores the proposed desired state. ApplicationSet can generate Argo CD Applications from matching repository configuration. Argo CD reconciles them.

Git-first workflow
⌁

Propose

Update Release Repo writes or updates configuration and opens a pull request for review.

Git change
◈

Reconcile

After merge, ApplicationSet and Argo CD process the desired state through their respective reconciliation loops.

GitOps
♥

Verify

An optional Verify step evaluates configured telemetry, such as Kubernetes replica metrics in Datadog.

Health signal
Keep these outcomes separate: PR merged ≠ ApplicationSet reconciled ≠ Argo CD sync succeeded ≠ application healthy.

03 / ApplicationSet

One template, multiple Applications

ApplicationSet uses a generator to provide parameters and a template to define generated Argo CD Applications.

🧬

ApplicationSet

Defines how Applications should be generated. It is a higher-level resource, not the application workload itself.

Generator + template → Application resources
🔄

Argo CD Application

Represents an application Argo CD manages. Argo CD compares desired state with actual state and synchronizes resources.

Generated Application → managed resources

04 / Git generator

Configuration in Git drives Application creation

The file-oriented Git generator can read matching configuration files such as config.json and expose their data to an ApplicationSet template.

gitops-config/
└── environments/
    ├── development/
    │   └── config.json
    ├── staging/
    │   └── config.json
    └── production/
        └── config.json

Each configuration file describes environment-specific values. The configured generator must match the intended paths.

{
  "environment": "development",
  "replicaCount": 1,
  "region": "development"
}

Illustrative values only. The schema and how fields are consumed depend on the ApplicationSet template and target application configuration.

DiscoverGit generator scans configured paths.
ExtractMatching file data becomes template parameters.
RenderApplicationSet template uses the parameters.
ReconcileGenerated Applications are managed by Argo CD.

Consistency

Reuse a common template across environments.

Auditability

Git history captures changes and authorship.

Scale

Add matching configuration instead of hand-authoring each Application.

05 / PR pipeline

The four key activities

Harness coordinates the change lifecycle. The precise steps depend on whether the pipeline waits for a provider-side merge or uses explicit Harness approval and merge steps.

01
Update Release RepoCreate/update configuration and open PR.
02
Review & mergePR provider review is the gate in the wait-for-merge pattern.
03
GitOps SyncSynchronize configured application(s).
04
Fetch Linked AppsRetrieve the application linked to the workflow.
Pattern A

Wait for PR merge

Enable Wait for PR merge on Update Release Repo. The provider's review and merge process gates the next steps.

Update Release Repo (wait) ↓ Git provider review + merge ↓ GitOps Sync ↓ Fetch Linked Apps
Pattern B

Explicit Harness approval

The supplied YAML example uses a Harness Approval step and a separate Merge PR step.

Update Release Repo ↓ Harness Approval ↓ Merge PR ↓ GitOps Sync ↓ Verify
Do not accidentally combine both patterns without checking the intended control flow. They represent different ways to gate the pipeline.

07 / Continuous Verification

Sync success is not health success

The supplied example adds a Verify step and configures Datadog as a health source to inspect a Kubernetes replica metric.

🔄

GitOps synchronization

Checks whether desired configuration is synchronized through the configured GitOps workflow.

Desired state
📈

Continuous Verification

Analyzes monitored telemetry to help assess whether the deployment is behaving as expected.

Observed signals

Example Datadog query

The source material lists kubernetes_state.deployment.replicas_available as an example metric, but its manual query uses a different metric name. Confirm the intended metric in your Datadog account.

avg:kubernetes_state.deployment.replicas{kube_app_instance:gitops-sample-application}

Example tag:

kube_app_instance:gitops-sample-application

Example Service Instance Identifier (SII):

kube_app_instance
Interpret carefully: Replica availability alone does not prove application correctness. Use metrics that match the application's reliability objectives and verify the exact Datadog query and tags before production use.
Example Verify settings in the supplied YAML
  • Duration: 10m
  • Sensitivity: HIGH
  • Baseline: LAST
  • failOnNoAnalysis: true
  • Manual intervention for verification failures and unknown errors.
These are example settings, not universal recommendations.

10 / WSO2 Project 702

Map the pattern to OpenChoreo

Project 702 proposes PR-driven self-service GitOps using Backstage, occ, GitHub, Flux, and OpenChoreo controllers.

Suggested conceptual architecture
1
BackstageDeveloper inputs / scaffolder
2
occGenerate OpenChoreo manifests
3
GitHub PRReview and merge
4
FluxReconcile Git desired state
5
OpenChoreoControllers reconcile resources
6
Portal statusReport progress and outcome

Useful ideas to reuse

  • PR as an approval boundary.
  • Separate merge from reconciliation.
  • Track which resource a PR affects.
  • Show pending changes and synchronization status.
  • Consider health verification after the core loop works.

Do not copy blindly

  • ApplicationSet is Argo CD-specific; Project 702 initially focuses on Flux.
  • Harness pipeline steps are not Backstage actions.
  • Do not bypass GitOps reconciliation with direct deployment calls.
  • Do not treat metrics as a substitute for resource status.
  • Detect conflicts and surface them instead of silently resolving them.
Recommended first milestone: Backstage action → `occ` generation → GitHub PR → merge → Flux reconciliation → observable OpenChoreo resource status. Add runtime health verification only when the core loop is reliable.

Interactive resource mapping

ReleaseBinding

A PR action can render the resource with occ, resolve its configured destination path, create a GitHub PR, and later associate the merged change with reconciliation status.

11 / Implementation checklist

Questions to resolve before implementation

Harness and ApplicationSet
  • Does the Git generator match the intended config paths?
  • Does the template generate valid Applications?
  • Is the flow waiting for PR merge or using explicit approval and merge steps?
  • How is the newly generated Application discovered?
  • Which metric and tags are available in Datadog?
OpenChoreo Project 702
  • Which resource types should the first PR action support?
  • How will occ support configurable repository layouts?
  • How will the action detect conflicting open PRs?
  • How will the portal track merged-but-not-yet-synced changes?
  • Which source is authoritative for reconciliation status: GitHub, Flux, or OpenChoreo resource conditions?
  • Should runtime verification be part of the initial scope or a later extension?
