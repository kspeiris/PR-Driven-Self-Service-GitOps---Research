Port.io Workflows

A practical, detailed guide to Port’s workflow system and how its design patterns can inform WSO2 Project 702: PR-Driven Self-Service GitOps for OpenChoreo Developers.

1. What is Port?

Port is a developer portal and internal developer platform (IDP) product. It helps engineering organisations create a unified software catalog and self-service experiences, and coordinate actions across systems such as GitHub, CI/CD tools, cloud platforms, ticketing systems, and observability tools.

Port’s Workflows feature is a governed execution layer. It lets a platform team define an automation once, then expose it through a self-service form, a catalog event, an API, a schedule, or an AI agent, depending on the configured trigger types.

DiscoverCatalog software, services, teams, environments, ownership, and metadata.
RequestGive developers forms and controlled actions rather than asking them to learn every backend system.
OrchestrateConnect validation, branching, integrations, and external automation into one workflow.

What Port is—and is not

Port is not itself a replacement for Kubernetes, Flux CD, a Git provider, or every CI/CD engine. It coordinates operations across connected systems. Those systems remain responsible for their own work: GitHub manages repositories and PRs; CI executes builds; GitOps controllers reconcile desired state; Kubernetes runs workloads.

Core mental model: Port defines and governs the workflow; connected systems perform the underlying operations.

2. Port as an Internal Developer Platform

2.1 The developer problem

Without a self-service platform, a developer may need to ask another team to create a repository, change a deployment, open a ticket, provision an environment, or perform a release. The process can be slow, inconsistent, and difficult to audit.

Port can put a curated interface in front of those operations. Platform engineers define the allowed inputs and the workflow logic; developers use the approved interface.

2.2 The software catalog

Port’s catalog stores entities described by blueprints. A blueprint defines the structure of a type of entity, such as a service, team, environment, deployment, or workflow. Entity properties and relations provide context for workflows and portal pages.

Software Catalog ├── Service: payments-api │ ├── owner → Payments Team │ ├── repository → GitHub URL │ ├── environment → staging │ └── deployment status → healthy ├── Team: Payments Team └── Environment: staging | v Workflow can resolve known context and validate user input

The names above are examples. A real Port catalog uses the blueprints and properties configured by the organisation.

2.3 Why catalog context matters

A workflow can ask for a service entity rather than an arbitrary text string. That can reduce typos and let the workflow use known service metadata. However, the catalog must be populated and maintained accurately; Port cannot infer reliable ownership or deployment data if the underlying integrations and schemas are missing or stale.

3. Port Workflows Architecture

Port describes each workflow as a directed graph of nodes connected by edges. Nodes represent entry points, operations, or branching logic. Connections establish execution order and pass data between nodes.

DEVELOPER / EVENT / API / AI AGENT | v Workflow Trigger | v Validate / Prepare Data | v Condition Node / \ path A path B | | v v Integration Action Webhook / Custom | | +---------+---------+ | v Update / Report Result | v Workflow Run Record
TriggerStarts the workflow and supplies inputs/context.
ActionPerforms an operation, such as a GitHub action or webhook call.
ConditionEvaluates expressions and selects a branch.
ConnectionDefines which node follows another and allows outputs to flow forward.

3.1 How a workflow is authored

Port’s documentation describes three approaches: visual editor, JSON editor, and AI-assisted workflow generation. The visual editor is useful for understanding the graph; JSON is useful for reviewing the exact configuration; AI generation can accelerate a draft but should not replace review and testing.

3.2 A workflow is not necessarily a CI pipeline

A Port workflow can trigger a CI pipeline, but it is broader than a build pipeline. It may combine catalog context, conditions, approvals, GitHub operations, webhooks, and status updates. Think of it as a cross-system orchestration layer.

4. Trigger Types

Port documents four trigger types. A workflow can define multiple triggers, so one workflow definition may support more than one entry point when configured accordingly.

Catalog eventA catalog entity is created, updated, or deleted.When a service entity is created, prepare onboarding tasks.React to a resource/catalog event where supported.

Trigger design principles

  • Keep inputs explicit, typed, and well-described.
  • Validate identifiers against authoritative data.
  • Define who may execute each entry point.
  • Do not assume all trigger types are automatically enabled or safe without configuration.
  • Make workflow titles and descriptions meaningful to both humans and agents.

5. Nodes, Connections, and Branching

5.1 Action nodes

Action nodes perform work. Port documents native integration actions for supported systems, plus webhook and other execution patterns. The exact nodes available depend on Port’s current capabilities and the installed integrations.

5.2 Condition nodes

Conditions use JQ expressions. Each branch has an expression; Port evaluates the options and follows the first matching expression, or a fallback path if no expression matches. The order and fallback behaviour should be tested carefully.

5.3 Connections

A connection links a source node to a target node. Outputs from earlier nodes can be referenced by later nodes, allowing the workflow to use a result such as a created PR URL in a subsequent status update or notification.

trigger ──> validate ──> condition ├── valid ──> create-pr ──> report-success └── invalid ─────────────> report-error
Design advice: Make failure paths visible. A workflow should not quietly continue when validation or PR creation fails unless that behaviour is explicitly intended.

6. Data Flow, Outputs, and JQ

Port workflow nodes can produce outputs. Later nodes use expressions to read those outputs and construct payloads. Port uses JQ expressions for conditions and data mapping.

6.1 Conceptual example

Suppose a trigger receives a service identifier and a target environment. A later action needs those values in its payload. The workflow can reference the trigger’s output fields instead of hard-coding the values.

{
  "service": "{{ .outputs.trigger.service }}",
  "environment": "{{ .outputs.trigger.environment }}"
}

This illustrates Port’s documented output-template style used in examples. The exact syntax depends on the action configuration field and Port’s current workflow schema; use the official docs when implementing it.

6.2 Example condition logic

Conceptually, a workflow could choose one branch for a staging target and another for production. The condition expression must use the data shape available at runtime.

# Conceptual JQ expression only — adapt to the actual node input
.outputs.trigger.environment == "production"

Do not paste this expression blindly into a workflow: verify the expression context and exact syntax in the current Port editor and documentation.

6.3 Why data mapping matters

  • It passes user input to connected systems.
  • It makes branching decisions data-driven.
  • It enables an action result to inform later nodes.
  • It can reduce duplicated configuration across workflows.

7. GitHub Integration and Pull Requests

Port’s GitHub integration actions can trigger GitHub Actions workflows, create or update pull requests, and create issues. These actions use the configured GitHub integration and its credentials. Repository and token/app permissions must allow the requested operation.

7.2 Requirements and caveats

  • A GitHub integration must be installed in the Port organisation.
  • The integration needs the permissions required by the operation, such as write access to pull requests for PR creation.
  • Triggering a GitHub Actions workflow requires a suitable workflow in the target repository and the expected dispatch configuration.
  • For self-hosted Ocean installations, action processing may need to be enabled explicitly. The current docs specify configuration such as enabling the actions processor.
  • Do not place secrets into ordinary workflow inputs or assume every action supports secret references. Port’s integration-action overview notes limitations around secrets in integration actions.

7.3 PR creation is not deployment

Port creates PR | v Git provider review / checks | v PR merged | v GitOps controller observes desired state | v Reconciliation + health evaluation | v Application status

The PR is the reviewable change mechanism. GitOps is the deployment/reconciliation mechanism. A successful PR creation or merge does not prove that the application deployed successfully.

8. Self-Service Workflows

Port’s self-service model lets platform teams create reusable developer experiences for routine tasks while connecting those experiences to existing infrastructure and automation.

Common examples

Scaffold a serviceCreate a repository or start a service template.
Provision a resourceRequest an environment or cloud resource.
Deploy or redeployTrigger a delivery workflow for a selected version.
RollbackStart an approved rollback operation.
Scale an applicationRequest a replica-count change.
Update catalog stateReport a workflow result or update relevant metadata.

What makes a self-service workflow good?

  1. It asks for the minimum required inputs.
  2. It resolves known context from the catalog where possible.
  3. It validates input and permissions before performing changes.
  4. It makes side effects explicit.
  5. It exposes progress and failure reasons.
  6. It returns useful outputs such as a PR link or execution link.
  7. It leaves a trace that helps teams understand who requested what and what happened.

9. Permissions, Approvals, and Governance

9.1 Execute permissions

Port workflow permissions control who can invoke a workflow. The documentation describes role, user, team, and policy-based restrictions, including restrictions based on the source of an invocation. Workflows without explicit execute permissions default to Admin-only under the documented behaviour; admins can always execute workflows.

9.2 Read/write versus execute permissions

Permission to view or edit a workflow definition is separate from permission to execute it. This distinction matters: a developer may be allowed to request an approved operation without being allowed to change the automation that performs it.

9.3 Organization-level execution context

Port documents that workflows execute with organization-level permissions. That can exceed the privileges of the person who created the workflow. Consequently, workflow owners must review and scope actions carefully to prevent privilege escalation or unintended access.

9.4 Human approvals and policy checks

Approval and policy mechanisms can be used as guardrails for sensitive operations. Exact approval configuration depends on the trigger and workflow features available in the current Port release.

Security rule: A workflow that can create PRs, trigger deployments, or modify infrastructure is privileged automation. Restrict who can invoke it, validate all inputs, scope integration permissions, and test both UI and API/MCP invocation paths.

9.5 Example governance matrix

Workflow definition editsRestricted workflow catalog write permissions.
AI/MCP invocationRestrict eligible workflows and invocation source; validate machine-token policies.

10. Workflow Runs, Logs, and Status

Port provides workflow testing and run-level visibility, including step-by-step execution and logs according to its current workflow documentation. These capabilities help operators see which node ran, what succeeded, and where a failure occurred.

Statuses should represent different facts

SignalWhat it tells youWhat it does not prove
Workflow run succeededThe configured workflow execution reached its success outcome.It does not automatically prove that a downstream app is healthy.
PR openedA proposed repository change exists.The change is not yet accepted or deployed.
PR mergedThe repository accepted the change.GitOps reconciliation may still fail.
GitOps syncedThe controller reports desired-state synchronization.The application may still be unhealthy.
Application healthyThe relevant health checks report a healthy application.It does not prove the workflow's governance was correct.

For Project 702, the same separation is essential. The Backstage UI should not display “deployment successful” merely because the PR was created or merged.

11. MCP and AI Agents

Port documents that self-service workflows can be exposed as tools through its MCP server. An agent can discover available workflows, read their descriptions and input schemas, and invoke the matching workflow. The same workflow permissions are relevant to human and agent invocation, subject to documented token and policy behaviour.

11.1 Documented discovery and execution pattern

User asks an agent to perform a task | v Agent discovers available self-service triggers | v Agent reads workflow description + input schema | v Agent resolves the required inputs | v Agent invokes the workflow | v Workflow validates and executes configured logic | v Agent reports result / run link

The Port documentation names tools including list_self_service_triggers for discovering executable workflow triggers and trigger_run for invocation. Exact tool behaviour and schemas should be verified against the live documentation.

11.2 What this means for platform engineering

The agent does not need to invent an unrestricted deployment procedure. Instead, it selects a platform-engineer-defined workflow, provides structured inputs, and lets that workflow apply its validations, permissions, and execution logic.

11.3 Important security caveat

Port documents different permission behaviour for machine tokens and personal access tokens. Machine tokens may bypass static role/user/team checks by default, while policy checks can still be used to restrict invocation. AI/MCP should therefore be introduced only after permissions and source restrictions are understood and tested.

11.4 Relevance to Project 702

MCP support is an optional extension, not a prerequisite for the Project 702 MVP. First establish deterministic PR generation, validation, and status tracking. An agent interface can later invoke the same self-service workflow if the architecture is designed to expose a safe, stable operation.

12. Software Catalog and Workflow Context

The catalog is useful because it provides structured information that a workflow can use to guide execution. For example, a service entity might include its owner, repository, language, lifecycle, deployment environment, and related resources.

12.1 Example entity model

Service blueprint properties: identifier repository URL lifecycle language owner relations: team environment deployment | v Self-service workflow resolves service | v Validates ownership / target / required metadata | v Performs approved operation

12.2 Keep catalog data trustworthy

  • Define clear property types and identifiers.
  • Synchronize data from authoritative systems where practical.
  • Define ownership and update responsibility.
  • Do not use catalog metadata as a substitute for authorization checks.
  • Handle missing or stale metadata as an explicit validation outcome.

For OpenChoreo, the existing component, project, environment, release, and deployment concepts should remain authoritative for the platform. A Port catalog model is a useful design reference, not a reason to create duplicate sources of truth.

14. Port Concepts Applied to OpenChoreo Project 702

Your project is titled PR-Driven Self-Service GitOps for OpenChoreo Developers. The objective is to let developers request supported deployment changes from the existing Backstage portal while ensuring the changes are represented as reviewable GitHub pull requests.

14.1 What OpenChoreo already provides

The supplied OpenChoreo UI reference describes OpenChoreo as a modular, Kubernetes-oriented internal developer platform with a Backstage-powered portal, CI/CD, GitOps, and observability. It documents component, release, environment, and deployment-related developer experiences.

The supplied repository review says the MVP work belongs primarily in the Backstage plugins; it identifies existing occ generation capabilities and an existing GitHub PR action, while GitOps-specific Scaffolder actions and status tracking need implementation.

14.3 The most important lesson

Do not copy Port’s implementation wholesale. Borrow the design pattern: one well-defined self-service request, explicit inputs, validation, branching, integration, auditability, and status reporting. Implement those responsibilities with the existing Backstage Scaffolder, occ, GitHub integration, and Flux/OpenChoreo architecture.

15. Recommended Project 702 Architecture

OPENCHOREO PROJECT 702 Developer | v Existing Backstage Portal | v Scaffolder Template / Form | v Validate Inputs + Authorization + Conflict Check | v Custom GitOps Scaffolder Actions | +---- invoke existing `occ` generation | +---- write generated OpenChoreo resources | +---- prepare repository change | v Git Branch + Commit | v GitHub Pull Request | +---- reviews / branch protection / CI | v Merge into tracked GitOps branch | v Flux CD (existing GitOps controller) | v OpenChoreo Control Plane Reconciliation | v Kubernetes workload / environment | v Status correlation back to portal

15.1 Core implementation requirements

  1. Use existing resource generation. Reuse the documented occ generation commands where appropriate rather than hand-building OpenChoreo resources with ad-hoc templates.
  2. Account for runtime packaging. The repository review notes that occ is not already packaged in the Backstage backend image; decide how the executable will be installed and invoked safely.
  3. Detect conflicts. Check the repository and relevant resource state before publishing changes.
  4. Reuse the GitHub PR integration. Do not build a parallel PR mechanism without a clear reason.
  5. Prevent GitOps bypasses. In GitOps mode, supported promotion and override operations should not silently mutate the live control plane through direct API writes.
  6. Track the full lifecycle. Correlate request → PR → merge revision → Flux reconciliation → final resource/application status.

15.2 Promotion and overrides

The supplied OpenChoreo reference describes a ComponentRelease as an immutable release snapshot and ReleaseBinding as the environment association. Promotion may create or update the relevant ReleaseBinding. Overrides can require separate environment-specific YAML changes, so do not assume the release-binding generator handles all override work.

16. Limits, Risks, and Design Decisions

Open BetaPort Workflows may change. Confirm feature availability and API behaviour before production dependency.
Integration dependencyA workflow can only perform an external action if the integration, credentials, permissions, and runtime are configured.
Not a GitOps controllerPort can orchestrate changes, but Flux or another controller handles reconciliation in the target design.
Not automatic status correlationPR status, GitOps status, and application health require explicit data integration.
Privilege riskWorkflow actions can execute with organization-level permissions. Restrict and audit them.
Catalog qualityBad or stale catalog metadata can lead to poor context or incorrect workflow decisions.

Decisions to make before implementation

  • Which operations must create a PR and which remain direct operations?
  • What repository and branch are authoritative for Flux?
  • What is the required conflict-check strategy?
  • How will the system handle duplicate requests and retries?
  • What permissions and review policies are required for production?
  • How will PRs be correlated with GitOps and application status?
  • Which information is safe to include in logs and workflow outputs?

Build the form, validation, conflict checks, occ generation, file writing, and GitHub PR creation.

MVP priority
Phase 2 — Lifecycle status

Track PR open/merge state, relevant revision, Flux reconciliation, and final deployment status.

MVP completeness
Phase 3 — Overrides through PR

Add environment-specific override generation, validation, and PR flow.

Next capability
Phase 4 — Advanced workflows

Add richer policies, notifications, additional self-service operations, or MCP/AI integration after core reliability is established.

Optional extension

Definition of done for the first workflow

  • A valid request creates a PR containing the expected OpenChoreo configuration.
  • An invalid request fails with a clear explanation.
  • A conflict prevents unsafe publishing.
  • A generation or GitHub error does not produce a false-success result.
  • PR creation is clearly separated from deployment success.
  • The portal provides a useful link and task/request identity.
  • Credentials are not exposed in logs or generated files.

Debugging order

  1. Identify which stage failed: input, generation, Git operation, PR, GitOps, or application health.
  2. Read the exact error and related logs.
  3. Check credentials and permissions without printing secrets.
  4. Confirm the repository, branch, and generated diff.
  5. Inspect GitOps controller status and target resource events.
  6. Report the correct state back to the portal.

Final takeaway

Port’s key idea is to define a governed workflow once and make it available through a suitable entry point, with explicit context, branching, integrations, permissions, and execution visibility. For Project 702, the valuable pattern is not to recreate Port itself. It is to deliver the same kind of reliable self-service experience through OpenChoreo’s existing Backstage portal, Scaffolder, occ, GitHub pull requests, Flux CD, and status tracking.
