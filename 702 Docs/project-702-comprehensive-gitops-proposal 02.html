Project 702 · Design research and implementation

PR-Driven Self-Service GitOps for OpenChoreo Developers

A proposal for turning developer intent in the existing OpenChoreo Backstage portal into a validated, conflict-aware Git change and a reviewable pull request—ending the core MVP at a successfully merged PR.

MentorVajira Jayasrimal
Duration6 months
Team1 contributor
MVP providerGitHub + Flux-compatible GitOps
Primary outcome: PR opened & mergedExisting Backstage portalReuse occ CLINo controller changes in MVP
Scope boundary: this proposal specifies the complete workflow from discovery and design through portal interaction, validation, conflict checks, manifest generation, branch/commit creation, pull-request review and merge. Flux reconciliation and runtime readiness are described as the next hand-off, not required for the MVP completion gate.

02 · Problem statement and current-state evidence

The project closes the gap between OpenChoreo's developer portal and a GitOps repository, without rebuilding the platform or replacing existing deployment abstractions.

↯

Direct-write portal actions

Current portal actions call OpenChoreo APIs directly. In GitOps-managed environments, these writes bypass Git review and can be overwritten by reconciliation.

⌘

Manual GitOps authoring

Developers may have to author or update OpenChoreo YAML and commit it themselves even for a routine release promotion.

⛓

Disconnected existing tools

occ can generate relevant manifests in file-system mode, and existing sample workflows can open GitOps PRs, but there is no generalized self-service PR path in the portal.

03 · Goals, non-goals and MVP boundary

Goals

  • Allow a developer to initiate release promotion from the existing Deploy tab.
  • Validate source/target against the configured deployment pipeline.
  • Generate the intended OpenChoreo resource using existing occ functionality.
  • Detect overlapping open PRs and merged-but-not-yet-synced changes before publishing.
  • Create a reviewable GitHub PR with deterministic, traceable metadata.
  • Show the PR URL, state and relevant conflict explanation in the portal.
  • Make repository target paths configurable rather than hard-coded.
  • Use least-privilege credentials and avoid secret leakage.

Non-goals for the initial MVP

  • Changing OpenChoreo controllers or CRD behaviour.
  • Automatically merging PRs or automatically resolving Git conflicts.
  • Replacing build workflows or the existing release model.
  • Shipping a complete multi-provider implementation. GitLab and other providers are researched/design targets; GitHub is the implementation target.
  • Building a new standalone portal that duplicates OpenChoreo.
  • Making runtime readiness a hard completion requirement for the PR-creation MVP. It is an integration hand-off / later status enhancement.

Security

Least-privilege GitHub access, secret redaction, no credentials in generated manifests or logs, reuse identity/authorization.

Reliability

Idempotent checks, clear failure boundaries, no partial PR on generation failure, safe retry behaviour.

Maintainability

Small typed action contracts, unit-tested path resolution, pinned CLI version and configurable repository layout.

Usability

Explain conflicts with actionable PR links; do not silently overwrite a developer's existing change.

Compatibility

Reuse OpenChoreo CRDs and existing Backstage plugin conventions; no new controller API required for MVP.

Structured task logs, correlation ID, durations and action outcomes without logging tokens or secret values.

08 · Conflict detection design

The goal is safe detection and clear developer choice—not automatic conflict resolution.

Conflict cases

Case A · Open PR overlaps target

List open PRs for the configured repository/base branch. Compare changed file paths to the resolved ReleaseBinding path. If the target path is already changed, stop before publishing a second PR.

Hard stop by default

Case B · Merged but not yet synced

A prior PR is merged, but the observed GitOps revision has not advanced to include its merge SHA. A new request may be based on stale desired state; warn or block based on the reliability of the revision source.

Requires revision signal

Case C · Branch/base moved

Between conflict check and PR creation, base branch changes. Recheck target files / base SHA before publish or let GitHub's normal branch comparison reveal the race; fail safely when overlapping intent is discovered.

Race protection

Case D · Git merge conflict

The target branch and proposed branch cannot be merged cleanly. Do not auto-resolve. Surface GitHub conflict state and direct the developer to the PR or a fresh run.

Human resolution

Recommended algorithm

input: repo, baseBranch, component, namespace, project, targetEnvironment
path = resolveTargetPath(layoutConfig, resourceContext)
if !authorized(user, "promote", component, targetEnvironment):
    return DENIED
validatePromotionPath(deploymentPipeline, sourceEnvironment, targetEnvironment)
openPRs = scm.listOpenPullRequests(repo, baseBranch)
for pr in openPRs:
    changedPaths = scm.listChangedFiles(pr)
    if pathsOverlap(changedPaths, path):
        return CONFLICT(prUrl, prNumber, author, changedPaths ∩ path)

baseSha = scm.getBranchHead(repo, baseBranch)
pendingMerge = findMergedChangeNotObservedByGitOps(path, baseSha)
if pendingMerge is reliably detected:
    return PENDING_SYNC(pendingMerge)

workspace = checkoutRepositoryAt(baseSha)
runOccGeneration(workspace, resourceContext)
changed = inspectGitDiff(workspace)
assert changed is not empty
assert every changed path is allowed for this operation
validateGeneratedYAML(changed)
recheckBaseAndConflicts()  // narrow the race window
branch = deterministicBranchName(context)
commitOnly(changed, branch)
pr = createPullRequest(branch, baseBranch, title, body, labels)
return CREATED(pr.url, pr.number, branch, changed)

Path overlap rules

  • Exact target path match is a conflict.
  • If an operation is allowed to update a directory, any changed file within that directory is a conflict.
  • Normalize separators and reject path traversal such as ../; compare repository-relative canonical paths.
  • For MVP promotion, scope the write allowlist to the resolved ReleaseBinding manifest. Do not infer overlap solely from PR title or branch name.
  • Do not treat every PR in the repository as a conflict; only resource/path overlap or a relevant pending merge should block the request.
Important nuance: a deterministic branch plus update: true may silently update an existing PR for the same component/environment. The conflict gate must define when that is safe. Default MVP behaviour should surface the existing PR and require an explicit update/reuse choice rather than unexpectedly overwriting it.

09 · Branch, commit, pull request and merge policy

Branch and idempotency

  • Use a predictable branch identity for the resource/action, for example gitops/promote/<namespace>-<component>-<target-environment>, with safe slugging and length limits.
  • Use the PR's structured metadata and file diff as the source of truth—not branch naming alone.
  • Before reusing an existing branch/PR, run the conflict policy and tell the user whether the existing PR will be updated.
  • Keep each PR narrowly scoped to the intended manifest change. Fail if unrelated files are modified.
  • Use a clear commit message, e.g. gitops: promote biocare-web to staging.

10 · Security, authorization and credential design

Credential strategy

  • Use Backstage SCM integration and the configured GitHub credential provider.
  • Choose user-attributed OAuth or a service/bot identity with the mentor/platform team's agreement.
  • Prefer a GitHub App or tightly scoped token for repository write + PR permissions.
  • Store secrets in approved Backstage configuration/secret management; never commit them into the GitOps repository.
  • Do not log Authorization headers, tokens or environment-secret values.

Authorization and trust boundaries

  • Reuse existing OpenChoreo ABAC checks, including promotion/environment permissions.
  • Validate repository and branch against trusted configuration; do not let arbitrary user input select an untrusted repo.
  • Run occ in an isolated temporary workspace with timeouts and bounded output.
  • Restrict generated paths and commit only reviewed output files.
  • Use normal GitHub branch protection; do not give the action permission to bypass reviews.

Operational safeguards

  • Pin the occ version compatible with the deployed OpenChoreo schema and document upgrade steps.
  • Validate all names/paths to prevent path traversal or shell argument injection; invoke subprocesses without unsafe shell interpolation.
  • Ensure temporary clones and workspaces are cleaned after success/failure.
  • Use structured, sanitized error messages and a correlation ID across Scaffolder actions.
  • Keep the GitHub token out of template form values, task output and PR body.

12 · Configuration, path model and action contracts

Repository configuration

Reuse the current release-config.yaml model where possible for MVP. Existing file-system mode uses default output directory and project/component mappings, not arbitrary placeholder templates. If pattern-based paths are required, implement a resolver in the plugin or propose upstream support rather than assuming the CLI already accepts placeholder patterns.

# Illustrative configuration concept — adapt to the actual release-config.yaml schema
openchoreo:
  gitops:
    enabled: true
    provider: github
    repository: org/platform-gitops
    baseBranch: main
    conflictPolicy: block-on-overlap
    pullRequest:
      draft: false
      labels: [openchoreo, gitops, promotion]
      reviewersFromRepositoryPolicy: true
    occ:
      version: ""
      timeoutSeconds: 60

Path resolution principles

  • Resolve paths from trusted repository configuration and resource context, never from unchecked free-text form input.
  • Use the repository's existing layout conventions for the first MVP.
  • Expose the resolved target path in the review step before publication.
  • Canonicalize and validate repository-relative paths; reject traversal and out-of-scope changes.
  • Test the same operation against the default layout and at least one alternate configured layout if pattern support is delivered.

13 · Testing strategy and acceptance criteria

Test levels

Unit

  • Path resolver and canonicalization
  • Pipeline transition validation
  • Conflict overlap rules
  • Action input/output validation
  • occ process exit handling
  • Secret redaction

Integration

  • Scaffolder action registration
  • GitHub mock/API integration
  • Checkout, render and diff allowlist
  • Branch/commit/PR creation
  • GitHub permission failure
  • Retry and idempotency behaviour

End-to-end

  • Portal promotion creates PR
  • PR contains expected ReleaseBinding
  • Reviewer approves and merges
  • Merge SHA is captured
  • Conflict scenario blocks second PR
  • Direct API path is not invoked in GitOps mode

Acceptance criteria

  • A developer can initiate a valid promotion from the existing Deploy tab without hand-authoring YAML.
  • When GitOps mode is enabled, the portal creates a GitHub PR rather than directly mutating the ReleaseBinding through the OpenChoreo API.
  • The rendered manifest is generated using a supported occ command and matches the selected component/release/environment.
  • The PR changes only the expected resource path(s); no unrelated files are committed.
  • A second request for the same target resource detects the existing open PR and does not silently overwrite it.
  • Invalid promotion paths, missing permissions, missing CLI and rendering errors fail safely before PR creation.
  • The created PR has a useful title/body, correct base branch, traceable resource metadata and a URL displayed to the developer.
  • GitHub protected branch rules and review requirements cannot be bypassed by the action.
  • A reviewer can merge the PR normally; the operation records PR number, merge state and merge SHA where available.
  • Automated tests cover normal flow, conflict flow, command failure and GitHub API failure.
  • Documentation and a repeatable demo explain setup, configuration, limitations and troubleshooting.

Core demonstration scenario

  1. Start the local OpenChoreo/Backstage environment and configure a throwaway GitHub GitOps repository.
  2. Open a component's Deploy tab and select a valid source/target promotion.
  3. Show the resolved path and conflict check.
  4. Confirm the generated ReleaseBinding diff and open PR in GitHub.
  5. Open a second promotion targeting the same resource and show that the existing PR is surfaced rather than silently updated.
  6. Review the PR, satisfy repository checks, merge it with an authorized account, and capture the merge SHA.
  7. Optionally show Flux detecting the merge as a post-MVP hand-off demonstration.

Engineering deliverables

  • GitOps configuration/feature flag for the existing portal.
  • Scaffolder promotion template and custom validation/conflict/render actions.
  • Packaged and version-pinned occ runtime.
  • GitHub branch/commit/PR publishing integration.
  • Deploy-tab PR mode with clear result/error UX.
  • Conflict check for open PRs touching the same target path.
  • Unit, integration and end-to-end tests.

Research and project deliverables

  • Comparison of Backstage SCM actions, OpenChoreo sample-gitops workflow and Red Hat Developer Hub/Argo CD patterns.
  • Documented configurable layout and credential model.
  • Conflict/pending-state design and decision record.
  • GitHub vs GitLab/provider comparison.
  • Installation, configuration, troubleshooting and developer documentation.
  • Recorded demonstration of promotion → conflict check → PR → review → merge.
  • Summary of stretch work and upstream CLI recommendations.

Definition of done

The project MVP is complete when: a permitted developer can initiate a valid promotion in the existing OpenChoreo portal; the backend checks for overlapping changes; occ generates the expected ReleaseBinding manifest; only the intended file is committed to a GitHub branch; a reviewable PR is opened and linked in the portal; a second overlapping request is safely surfaced; and an authorized reviewer can merge the PR under normal repository rules. The merge SHA and action metadata are recorded, tests pass, and the flow is documented and demonstrated.
