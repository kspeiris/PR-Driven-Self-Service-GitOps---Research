Executive summary

OpenChoreo already combines a Backstage-powered portal, occ manifest generation, GitOps support through Flux CD or Argo CD, and Kubernetes-native control-plane reconciliation. The project closes the gap between those pieces by making developer actions PR-driven.

The portal runs a Scaffolder workflow, renders the required OpenChoreo resources, creates or updates a Git branch and PR, and then leaves deployment to the GitOps operator after merge.

Success definition

  • No manual YAML for routine promotion.
  • Every developer-initiated desired-state change is reviewable in Git.
  • Existing occ semantics are reused.
  • Overlapping concurrent changes are detected before duplicate PRs.
  • The portal can expose the change lifecycle from PR to Ready/Blocked.
Research boundary: the project detects and surfaces overlapping changes; it does not automatically resolve arbitrary Git merge conflicts. That is an explicit non-goal of this project.
01 · Context

Problem, motivation & research gap

No portal audit trail

Direct portal API actions can change the cluster without Git history or PR review.

Manual GitOps YAML

Routine promotion can still require a developer to hand-author a ReleaseBinding.

Tooling not connected

occ can generate manifests, while existing build workflows demonstrate GitOps PRs, but the capability is not generalized as a portal self-service action.

Generation dependency gap

Generation can fail when application-level resources exist without platform resources such as ComponentTypes and Traits.

Questions the project must answer

  • How does the portal represent an open PR that has not synced?
  • How is repository layout configurable?
  • How are credentials and PR authorship handled?
  • How are concurrent changes surfaced?

These questions align with GitHub Discussion #3100.

04 · Technical design

Scaffolder actions, layout & occ

Custom

openchoreo:gitops:check-conflicts

List open PRs and compare changed files/target paths with the requested resource.

Custom

openchoreo:gitops:render

Run occ, write manifests into the Scaffolder workspace and stream logs.

Built-in

publish:github:pull-request

Use the existing Backstage GitHub action for branch, commit and PR publication.

Template sequence

steps:
  - id: validate
    action: builtin:noop

  - id: check-conflicts
    action: openchoreo:gitops:check-conflicts

  - id: render
    action: openchoreo:gitops:render

  - id: publish
    action: publish:github:pull-request

Configurable repository layout

openchoreo:
  gitops:
    repo: github.com?owner=acme&repo=platform-gitops
    baseBranch: main
    layout:
      releaseBinding: "namespaces/{namespace}/projects/{project}/components/{component}/release-bindings/{component}-{environment}.yaml"
      release: "namespaces/{namespace}/projects/{project}/components/{component}/releases/{release}.yaml"
      workload: "namespaces/{namespace}/projects/{project}/components/{component}/workload.yaml"

Hybrid dependency resolution

  1. Repository files first.
  2. Optional live-cluster fallback for ComponentTypes, Traits and cluster-scoped variants.
  3. Explicit fallback mode.
  4. Output identifies dependency source.
  5. Unit tests + upstream discussion before the change.
Implementation order: ReleaseBinding promotion → ComponentRelease → Workload → component creation. The guaranteed core stays narrow while the resource model can expand.
05 · Research contribution

Conflict detection & concurrent PR handling

The key contribution is conflict-aware orchestration, not blind automatic merge-conflict resolution.

Existing capabilities

  • Backstage GitHub actions can create branches, commit workspace files and open PRs.
  • The PR action supports update/reuse behavior for an existing branch/PR scenario.
  • PR UI plugins provide visibility and metrics.

Project-specific logic

  • OpenChoreo resource identity + deterministic target paths.
  • Detect overlapping open PRs before a second PR.
  • Show existing PR, author and state.
  • Choose view / update / cancel.

Interactive conflict-gate simulator

Choose conditions and evaluate.

Proposed algorithm

1. Resolve repository + deterministic target path.
2. List open PRs against the base branch.
3. Identify PRs touching the same target path/resource.
4. If overlap exists → show PR context and stop duplicate creation.
5. Otherwise → run occ → publish/update PR.
6. Never silently choose one side of an arbitrary Git merge conflict.
Plugin conclusion: research did not identify a published Backstage plugin dedicated to OpenChoreo-aware conflict detection/resolution. Existing PR visibility and built-in PR publication capabilities are complementary, not a replacement for this custom gate.

08 · Security

Credentials, permissions & reliability

Least privilege

Use appropriately scoped GitHub App/token credentials; never hard-code credentials.

Secret boundaries

Keep credentials in Backstage/Kubernetes secret infrastructure; never in the GitOps repo.

Retry/backoff

Retry transient SCM failures with controlled backoff; stop on validation or manifest-generation errors.

PR authorship

Compare user-authored vs bot-authored PRs for attribution, permissions and operational simplicity.

GitOps RBAC

Flux/Argo service accounts should have only required reconciliation permissions.

Template governance

Keep Backstage current and restrict template registration/modification.
